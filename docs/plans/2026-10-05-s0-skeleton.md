# S0: Skeleton and hygiene

Part of the [main plan](2026-10-05-raglab-plan.md) (phase P1, release v0.1).
This file is committed to the repo as `docs/plans/2026-10-05-s0-skeleton.md`.

## Goal

An empty but fully gated Python repo. Every later stage lands in a place where:
- formatting, types, tests, dependencies, secrets, SAST, workflow safety, privacy and the
  changelog are already checked on every PR;
- the two architecture rules (stdlib-only `core`, vendor SDKs only in `adapters/`) are enforced
  by tests that are proven to fail when broken.

No RAG code yet.

## Out of scope

Corpus, ingestion, models, Ollama, Docker image, deploy, playground, any API key. Those start in
S1a.

**What `make check` runs, in order:**
1. `ruff format --check`, then `ruff check`.
2. `pyright`.
3. `deptry`, then `vulture`.
4. `pip-audit`.
5. `bandit -r src`, then `semgrep` (Python rules, metrics off).
6. `zizmor .github/`.
7. `gitleaks` (the working tree and git history).
8. `node scripts/check-forbidden.mjs`.
9. `python scripts/check_architecture.py`.
10. `pytest -m "not live and not judged and not guardrails and not perf"`.

**pytest markers** are registered with `--strict-markers` so an unknown marker is an error:
- no network: `unit`, `contract`, `ingestion`, `retrieval`, `e2e_fake`, `security`, `ocr`;
- need keys: `live`, `judged`;
- `guardrails`, `perf`.

**`.gitignore`** covers:
- `.env*`, except `.env.example`;
- `privacy/forbidden-strings.txt`;
- `.venv/`, caches, `runs/tmp/`;
- `.claude/settings.local.json`, `.mcp.json`.

**`CLAUDE.md`** carries the rules that live only in this account's memory today, so a second
account follows them too:
- no AI attribution in commits or PRs;
- PRs only, merged by you;
- the per-stage loop (planner, developer, judge, your review);
- the isolation rule: never open the prior client codebase, only re-implement;
- the privacy check and the hooks;
- "label lab practice as lab".

## Acceptance criteria

Each criterion gives the evidence: the command and its expected result. **[CI]** means only CI
can prove it. **Break** means the judge breaks the item on purpose, checks the gate goes red,
then restores it. **Expected pass** means a break test that must *not* trip a gate.

## How it will run

1. **You approve this plan.** Your go message is quoted verbatim in the ledger.
2. **Setup, after asking you:** `brew install gitleaks`; `gh repo create
   willcoliveira/ai-testing-rag-lab --private`; clone; bootstrap commit to `main`; branch
   `chore/s0-repo-skeleton`.
3. **Developer (Opus 5.5)** builds and runs `make check`, recording evidence per criterion in
   the ledger.
4. **Judge (Fable 5.1, separate subagent, independent context)** re-runs every piece of evidence
   and does the break tests, restoring after each one. It runs `/security-review` on the branch,
   because S0 is security-relevant. Verdict per criterion: met, not met, or needs CI.
5. **Fix rounds:** at most two.
6. **Push the branch and open the PR.** The body is the stage report: n/19 met, the [CI] items
   to check, what was cut. No attribution.
7. **I verify AC10–AC12 on the PR.** You review from a separate checkout and merge by hand.
   S1a starts only on your go.

## Risks for this stage

- **semgrep registry rules need the network**, and some configs refuse `--metrics=off`. If that
  happens, the fallback is a small local ruleset committed under `.semgrep/`, noted in the
  ledger.
- **Dependabot's `uv` ecosystem** may not handle `ci-requirements.txt` with hashes. If it
  doesn't, that file gets its own `pip` entry.
- **Branch protection** depends on your GitHub plan, so it may wait for go-public (see AC17).
