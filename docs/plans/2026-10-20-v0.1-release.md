## What v0.1 is

The main plan: "v0.1 (S0–S4). A working, tested lab with real local results and a container ready
to deploy." At P1 the lab is experimental: fake and local models, so the numbers are real but local
(one maintainer's Mac). v0.1 ships prompt `answer-v1` with the abstention finding measured in S4 and
documented, not fixed (S4's D1).

## What the pull request does

1. **Carries in S4's CI record.** The S4 ledger's "CI on the PR" section, committed after #11
   merged, is cherry-picked as it is.
2. **Bumps the version.** 0.0.1 becomes 0.1.0 in `pyproject.toml` and `uv.lock`.
3. **Adds `make release-local`: the test slice, once.** It runs two things, both under gate
   `release` with provenance local:
   - the retrieval suite, default configuration (`config/retrieval-dense.toml`), on the test split,
     with the embedder only;
   - then one guarded `raglab ollama session`: the live contract test, then the generation suite
     (`config/local-ollama.toml`) on the test split, 3 trials.

   Both runs are made at one commit with a clean tree and both are published. The test split runs
   nowhere else.
4. **Runs the two history scans:** `make secrets` (gitleaks over the history) and
   `make privacy-history RANGE=--all` with the maintainer's real list.
5. **Writes the release notes**, `docs/releases/v0.1.0.md`. They hold:
   - what v0.1 is and how to run it;
   - every published run with its provenance;
   - the test slice's numbers, copied from the records;
   - the release-gate table, each row marked run, or not built yet with the stage that builds it;
   - the known limits.
6. **Writes `runbooks/release.md`**, the runbook the main plan's gate table names. It describes
   this lab release, and says what a production release adds and that this is lab practice: tags
   cut by CI with keys, the security suite and red team on the real model, trivy, an SBOM, signing
   and a deploy approval.
7. **Updates the CHANGELOG.** "Unreleased (v0.1)" becomes "v0.1.0 (2026-10-20)", with this pull
   request's line.
8. **After the merge, by hand:** the maintainer tags `v0.1.0` on the merge commit. A GitHub release
   made from the notes is optional and the maintainer's call.

**The test slice is reported, not gated.** No threshold is set from a test-split run, because the
split is held out: setting one would read it. v0.1's release "gate" is therefore that the test
slice ran, was published and is reported, and that the history scans are clean. The notes say this
is lab practice, and that production blocks a release on the security suite and agreed thresholds.
